# iOS 本地优先生日应用设计规格

- 日期：2026-08-21
- 状态：设计已确认，等待书面规格复核
- 适用项目：`birthday`
- 首发平台：iOS 17 及以上
- 后续平台：Android（不在本期实现范围内）

## 1. 背景与目标

现有项目是以 Node.js、Express、MySQL 和服务器邮件调度为中心的网页应用。生日列表、增删改、认证和邮件提醒都依赖服务器。项目已有移动网页适配和 WebAuthn 通行密钥，但没有移动端本地数据库、离线资源层、系统本地通知或增量同步协议。

本期新增一个 SwiftUI 原生 iOS 应用。应用采用本地优先架构：查看、搜索、添加、编辑、删除、农历换算和本地提醒都必须在无网络、服务器停机的情况下正常工作。现有服务器改为可选的跨设备同步、备份和邮件提醒服务，不得成为本地操作的阻塞条件。

### 1.1 成功标准

1. 飞行模式下可完整查看、添加、编辑和删除生日，重启应用后数据仍在。
2. iOS 本地通知默认在生日前一天和生日当天各提醒一次，服务器不可用不影响已经安排的提醒。
3. 首次绑定现有管理员账号后，可完整导入服务器中的生日数据；数量和关键字段核对一致。
4. 离线修改进入待同步队列，恢复网络后自动上传；重复请求不会产生重复记录。
5. 两台设备修改同一记录时不静默覆盖，冲突双方均可恢复。
6. 应用默认使用 Face ID 解锁，同步凭据只在首次绑定或失效时重新输入。
7. 第一版通过 Xcode 和 TestFlight 真机验证，体验稳定后再决定是否正式上架。

## 2. 用户与范围

### 2.1 目标用户

第一版仅供同一个管理员本人使用，可绑定自己的多台设备。服务器继续使用单管理员账号，不引入公开注册、家庭成员、角色或共享权限。

### 2.2 第一版功能

- 月历首页和当月生日列表
- 全部生日、搜索和按最近日期排序
- 新增、编辑、删除生日
- 农历月日、闰月和下一次阳历生日换算
- 生日前一天和生日当天的本地通知
- Face ID 本地解锁和系统设备密码回退
- 首次完整导入、增量双向同步和冲突处理
- 可选服务器邮件提醒
- 通知权限、提醒覆盖和同步健康状态
- 手动同步、设备解绑和重新绑定

### 2.3 明确不做

- Android 客户端实现
- 公开注册和多租户账户
- 家庭共享和协作权限
- 桌面小组件、Apple Watch、通讯录批量导入
- 多套自定义主题
- 无限数量的自定义提醒时间点
- 远程推送作为核心提醒通道
- 将现有网页套壳为移动应用

## 3. 方案选择

采用 SwiftUI 原生应用、SwiftData 本地数据库和现有 Node.js/MySQL 服务器增量同步的组合。

未选择 CloudKit 作为主同步层，因为后续 Android 无法自然复用，同时会让 MySQL、邮件服务和 iCloud 形成两套事实来源。未选择 PWA 或网页套壳，因为它无法稳定达到本地通知、Face ID、后台调度和原生视觉体验的目标。

## 4. 系统架构

### 4.1 iOS 应用边界

应用分为以下独立单元：

1. **SwiftUI 界面层**：月历、生日列表、编辑表单、设置、冲突处理和状态反馈。
2. **领域层**：农历换算、下一次阳历日期、提醒候选生成、验证规则。领域层不依赖界面和网络。
3. **本地数据层**：SwiftData 模型、查询、事务、软删除、本地迁移和待同步队列。
4. **同步层**：设备绑定、快照导入、批量上传、增量拉取、重试、游标和冲突保存。
5. **通知层**：权限检查、候选排序、滚动通知窗口、维护提醒和提醒健康状态。
6. **安全层**：LocalAuthentication、Keychain、应用锁定状态和敏感信息保护。

界面只调用领域用例，不直接调用网络或操作通知中心。同步层只通过本地仓库读取和写入数据；服务器响应必须先合并进本地数据库，再由界面观察本地变化。

### 4.2 服务器边界

服务器保留以下职责：

- 管理员账号的设备绑定和令牌撤销
- 首次完整快照
- 幂等的批量变更上传
- 基于单调递增游标的增量拉取
- 版本冲突检测和当前云端版本返回
- MySQL 持久化
- 可选邮件提醒

服务器不可用时，iOS 保存、查看和本地通知必须继续工作。同步错误不得转换为本地保存失败。

### 4.3 Android 后续兼容

未来 Android 使用 Jetpack Compose 和 Android 本地数据库重新实现界面与本地层。两端复用 UUID、字段语义、版本、软删除、幂等操作 ID、同步游标和冲突协议，不强制共用 UI 代码。

## 5. 数据模型

### 5.1 iOS 本地生日记录

`BirthdayRecord` 至少包含：

- `id`：稳定 UUID，与服务器主键一致
- `name`
- `lunarMonth`
- `lunarDay`
- `isLeapMonth`
- `reminderTimeMinutes`：当天 0 点起的分钟数，避免字符串格式差异
- `notifyDayBefore`
- `notifySameDay`
- `emailEnabled`
- `emailAddress`
- `emailMessage`
- `nextSolarDate`：可重新计算的缓存值
- `version`：最近一次服务器确认的记录版本
- `createdAt`
- `updatedAt`：展示和诊断用途，不作为同步先后依据
- `deletedAt`：软删除墓碑
- `syncState`：`synced`、`pending`、`conflict` 或 `pendingDelete`

农历换算使用中国农历规则生成公历日期。提醒时刻按设备当前本地时区的墙上时间解释；设备时区变化后重新计算通知，不修改用户选择的小时和分钟。

### 5.2 待同步操作

每次本地写操作在同一事务中追加 `SyncOperation`：

- `operationId`：每次操作的唯一 UUID
- `entityId`
- `operationType`：`upsert` 或 `delete`
- `baseVersion`
- `payload`：本次提交所需的完整可恢复数据
- `createdAt`
- `attemptCount`
- `nextRetryAt`
- `lastErrorCategory`

本地记录写入与待同步操作追加必须原子完成，避免出现界面已保存但没有同步凭据的状态。

### 5.3 服务器迁移

现有 `birthdays` 表增加：

- `version BIGINT UNSIGNED NOT NULL DEFAULT 1`
- `deleted_at DATETIME NULL`
- `notify_day_before TINYINT(1) NOT NULL DEFAULT 1`
- `notify_same_day TINYINT(1) NOT NULL DEFAULT 1`

新增 `mobile_sync_changes`，使用自增 `seq` 作为全局同步游标，记录实体、操作、版本和时间。新增 `mobile_sync_operations`，以 `operation_id` 为唯一键保存已处理操作结果，保证客户端重试幂等。新增 `mobile_device_sessions`，保存设备、刷新令牌哈希、有效期、撤销状态和最近使用时间。

现有网页新增、更新和删除路径也必须写入版本与变更日志，否则网页修改无法同步到手机。网页列表默认过滤 `deleted_at IS NOT NULL` 的记录。删除生日时保留生日墓碑，但停止并移除对应邮件提醒；恢复记录时根据完整提交内容重建邮件提醒。

## 6. 同步协议

### 6.1 设备绑定

第一版使用现有管理员用户名和密码完成一次设备绑定。服务器签发短期访问令牌和可撤销的设备刷新令牌。刷新令牌只存入 Keychain，并使用仅当前设备可用的保护等级；服务端只存令牌哈希。

Face ID 仅用于解锁本地应用，不充当服务器认证。认证失效时本地功能继续可用，只有同步暂停。

### 6.2 首次导入

1. 客户端完成设备绑定。
2. 下载服务器完整快照和当前游标。
3. 在本地事务中验证、写入并核对记录数量。
4. 任一记录解析或写入失败时整体回滚，不留下半套数据。
5. 手机已有数据时按 UUID 合并；姓名和生日疑似重复但 UUID 不同时，只提示用户确认，不自动删除。

### 6.3 增量循环

1. 用户操作先写 SwiftData，并追加待同步操作。
2. 网络可用时批量上传待同步操作。
3. 每个上传项携带 `operationId` 和 `baseVersion`。
4. 服务器事务性地验证版本、更新业务表、写变更日志并保存幂等结果。
5. 客户端标记成功项，保留失败项并按指数退避重试。
6. 客户端使用游标拉取增量，合并到本地后推进游标。
7. 数据合并完成后重建本地通知窗口。

同步触发时机包括应用启动、回到前台、本地修改后、用户手动刷新、网络恢复和系统提供的后台刷新机会。后台刷新只作增强，不承担准时提醒的正确性。

### 6.4 冲突规则

服务器仅在 `baseVersion` 与当前记录版本一致时接受修改。版本不一致时返回当前云端记录，不执行覆盖。

客户端保留本地版本和云端版本，并显示一次简洁选择：

- 保留本机：以云端当前版本为新基础重新提交本机完整内容
- 使用云端：用云端内容覆盖本地，并移除对应待同步操作

删除与离线编辑冲突时，界面提供“恢复并保留编辑”或“确认删除”。任何冲突都不得静默丢弃用户内容。

## 7. 本地通知设计

### 7.1 默认规则

每条生日默认生成两次提醒：生日前一天和生日当天，提醒时间使用记录中的本地墙上时间。用户可单独关闭其中一次，但第一版不提供无限自定义提醒点。

### 7.2 滚动窗口

应用为所有未删除记录计算通知候选，过滤已经过去的触发时间，按时间升序排列。保守安排最近 60 条生日通知，并额外安排 1 条覆盖期维护提醒，给系统内部限制保留余量。

通知窗口在以下时机重建：

- 应用启动或回到前台
- 新增、编辑或删除生日
- 同步合并完成
- 系统日期、时区或日历环境变化
- 系统提供后台刷新机会

设置页显示已安排通知数量和覆盖截止日期。维护提醒在覆盖期结束前触发，提示用户打开应用补充后续通知。后台任务执行时间由 iOS 决定，因此不得依赖后台任务临近生日才创建通知。

如果当天创建记录但所选提醒时间已经过去，应用明确询问“现在提醒一次”或“从明年开始”。

### 7.3 权限和失败状态

- 已授权：显示覆盖日期和待处理通知数量
- 权限受限或关闭：显示具体状态和跳转系统设置入口
- 安排失败：保留错误类别并允许重试，不显示虚假的“提醒已开启”

应用重建时只删除自己命名空间下的通知请求。通知标识符使用记录 UUID、提醒类型和公历日期组合，确保可更新和可取消。

## 8. 界面与交互

### 8.1 视觉方向

采用已确认的“现代空气感”：青绿和雾蓝为主色，轻玻璃层次、柔和阴影、清晰留白和适中的信息密度。遵循 iOS 动态字体、深色模式、减少动态效果和 VoiceOver 语义，不使用仅靠颜色表达状态的设计。

### 8.2 信息架构

底部标签栏包含：

1. **日历**：月历首页、生日标记、选中日期列表和提醒健康摘要
2. **全部**：搜索、最近日期排序、同步状态
3. **设置**：Face ID、通知、同步、设备、邮件和手动刷新

新增按钮位于日历和全部页面右上角，不作为标签栏项目。

### 8.3 新增与编辑

使用已确认的 iOS 原生分组表单：

- 基本信息：姓名、农历生日、闰月
- 提醒：时间、提前一天、当天、邮件备份提醒
- 补充信息：邮件地址和提醒内容

新增和编辑共用同一表单结构。验证失败时定位到对应分组并保留输入。删除操作需要确认；删除后本地立即隐藏并进入待同步状态。

### 8.4 首次启动和锁定

首次启动依次介绍离线能力、解释通知用途，再由用户触发通知权限请求。服务器绑定为可跳过步骤，跳过后应用从空的本地数据库开始使用。

应用默认启用 Face ID 锁定。认证失败时使用系统设备密码回退；设备不支持或未配置生物识别时，设置页显示真实状态，不伪装为已开启。

## 9. 错误处理

- 断网：显示“离线使用，稍后同步”，不作为阻断错误。
- 服务器失败：保留待同步队列和下次重试时间。
- 认证失效：暂停同步并提示重新绑定，本地数据继续可用。
- 冲突：保留本地和云端双方，等待用户选择。
- 导入失败：整个快照事务回滚。
- 本地写入失败：编辑页保持打开并保留输入，允许重试。
- 通知权限关闭：显示持续状态和系统设置入口。
- 农历日期无效：保存前给出具体字段错误；闰月不存在时不生成错误日期。

日志不得记录密码、访问令牌、刷新令牌、完整邮件正文或不必要的个人信息。同步和通知错误使用稳定分类码，界面显示中文可操作说明。

## 10. 测试与验收

### 10.1 单元测试

- 农历普通月份、闰月、跨年和下一次阳历日期
- 设备时区变化后的墙上提醒时间
- 两次提醒候选生成、过去时间过滤和最近 60 条排序
- 软删除、恢复和同步状态迁移
- 重试退避和游标推进

### 10.2 同步与服务器测试

- 快照导入数量和关键字段与当前 MySQL 一致
- 批量上传幂等，重复 `operationId` 不重复写入
- 版本匹配时更新成功，版本不匹配时返回冲突且不覆盖
- 删除与编辑冲突可恢复
- 网页端修改也生成移动端可拉取的变更
- 邮件提醒只在启用时创建，软删除后停止
- 认证令牌过期、刷新和撤销

### 10.3 UI 与真机测试

- 首次启动、跳过同步、稍后绑定
- Face ID 成功、失败和设备密码回退
- 离线新增、编辑、删除和重启恢复
- 月历、搜索、空状态和 100 条数据滚动性能
- 通知授权、关闭、重新开启和覆盖期维护提醒
- TestFlight 真机上的本地通知、后台刷新机会和网络切换
- 动态字体、VoiceOver、深色模式和减少动态效果

真实 Face ID、本地通知和后台行为必须在物理 iPhone 上验证，模拟器结果不能代替真机结论。

## 11. 实施阶段与时间

1. **iOS 本地核心与视觉系统**：2～3 个工作日完成视觉骨架，随后 5～7 个工作日完成 SwiftData、农历、编辑和本地通知。
2. **服务器同步与迁移**：4～6 个工作日完成表迁移、认证、快照、推拉、幂等和冲突。
3. **集成与 TestFlight**：3～5 个工作日完成导入核对、真机测试、无障碍和回归。

单人完整 MVP 预计 3～4 周。实施顺序必须先形成完全离线可用的 iOS 核心，再接入服务器同步；不得用临时服务器依赖代替本地领域能力。

## 12. 官方能力依据

- SwiftData 本地持久化：<https://developer.apple.com/documentation/swiftdata/preserving-your-apps-model-data-across-launches>
- iOS 本地通知：<https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app>
- 后台任务执行时机不保证：<https://developer.apple.com/documentation/backgroundtasks/bgtaskrequest/earliestbegindate>
- Apple 旧通知接口记录的 64 条保留边界：<https://developer.apple.com/documentation/uikit/uilocalnotification>

现行 `UNUserNotificationCenter` 文档没有承诺高于旧边界的待处理数量，因此本设计保守使用 60 条业务通知加 1 条维护提醒。该数量是风险控制选择，不是对现行系统硬上限的重新声明。
